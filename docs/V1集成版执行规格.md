# V1 集成版执行规格

> 2026-05-25 | Claude + Codex + 用户 三方对齐
> 测通 SU-03T 后即开工

---

## 一、架构红线

- **FSM (`fsm.cpp`) 负责状态追踪**：串口状态可见，后续可驱动 LED、MQTT status、小程序显示。`onEnter/onExit` 不放重逻辑，不放云调用。
- **`runConversationOnce()` 负责实际阻塞工作**：ASR → LLM → TTS → 播放，串行完成。
- **收尾统一 `gFsm.forceState(Idle)`**，不通过 `feed(TTS_DONE)` 收口（当前 FSM 代码 `TTS_DONE → Listening`，不是 `→ Idle`）。
- **`setup()` 必须显式进入 Idle**：初始化完成后调用 `gFsm.feed(Event::Kind::BOOT_DONE)`，否则 `loop()` 中的 `Idle-only` SU-03T 轮询不会生效。
- **先过板测闸门，再做 V1 集成**：先烧录 SU-03T 单测程序，确认唤醒帧、冷却时间、误触发情况，再进入云端语音 V1 集成。不要把“模块没测通”和“V1 集成问题”混在一起排查。

### 为什么不把云调用塞进 onEnter/onExit
- `Fsm::feed() → transit() → onExit/onEnter()` 是同步执行的
- 塞 ASR/LLM/TTS 进去 = 阻塞式巨回调，递归调用链深，异常恢复、超时、退出词都难处理

## 二、V1 范围（控制流纠偏）

| # | 功能 | 说明 |
|:--:|------|------|
| 0 | BOOT 收尾 | `setup()` 成功后 `gFsm.feed(BOOT_DONE)`，`Booting → Idle` |
| 1 | SU-03T 唤醒触发 | `loop()` 仅在 `Idle` 轮询 SU-03T，收到帧 → `runConversationOnce()` |
| 1.5 | 唤醒冷却时间 | `main.cpp` 里基于 `millis()` 做 `kWakeCooldownMs=2500` 的节流，避免同一句话或残留帧重复进对话 |
| 2 | 本地短提示音 | `playLocalBeep()` 写死一段 PCM，唤醒后立刻播放（~100ms 反馈） |
| 3 | beep 后洗 mic | beep 播放后丢 1~2 个 mic chunk，避免喇叭回声进 ASR |
| 4 | 单轮 ASR→LLM→TTS | `transcribeRealtime` → `chatCompletion` → `synthesizeRealtime`，沿用当前实现 |
| 5 | 播放后音频清洗 | `audio.stop()` + 连续 `readMicChunk()` 读 200ms 丢掉，非 `delay(2000)` |
| 6 | FSM 状态追踪 | `feed(WAKE_WORD/ASR_DONE/LLM_DONE)`；失败路径可补 `LLM_ERROR/TTS_ERROR`，保证串口/FSM 轨迹完整 |
| 6.5 | 阶段耗时日志 | 串口打印 `wake/asr/llm/tts/play/cleanup` 每阶段耗时，V1 验收以真实板测时间为准，不只看“能不能跑通” |
| 7 | 收尾 | `forceState(Idle)` 回到待机 |

### V1 显式不做
- 多轮循环（Listening ↔ Thinking ↔ Speaking）
- 超时计数退出（2× ASR_TIMEOUT）
- 退出词检测
- WS 长连接复用
- TTS ring buffer 流式播
- 停顿阈值调整（保留 800ms）

### V1 临时简化（加注释标记）
- **`Idle-only` 唤醒**：仅在 Idle 状态轮询 SU-03T。最终 `Monitoring` 也应可唤醒，`Alerting/Error` 不可。
- **MQTT 对话期间暂时饿住**：`runConversationOnce()` 阻塞期间 MQTT 心跳延迟。keepalive 60s，单轮最多十几秒，不断连。V1 不以“小程序实时同步状态”为验收目标，V2 处理。
- **LED/MQTT 展示按现状保留**：V1 先保证 FSM 状态追踪和串口可见，LED 状态灯与 MQTT 联动不是本轮必交项。
- **SU-03T 先做接收侧**：V1 只依赖 SU-03T → ESP32 的唤醒输入，不依赖 ESP32 → SU-03T 的控制命令链。

## 三、V2 范围（延迟优化）

| # | 功能 | 说明 |
|:--:|------|------|
| 1 | WS 长连接复用 | GatewayClient 加 `beginConversation()/endConversation()`，ASR/TTS WS 跨轮保持 |
| 2 | TTS ring buffer 流式播 | WS 收包→ring buffer→播放端取 buffer，两循环解耦，不用回调直播 |
| 3 | 多轮对话 | `TTS_DONE → Listening`，循环直到退出条件 |
| 4 | 超时计数退出 | 2 次连续 `ASR_TIMEOUT`（8s×2=16s 静默）→ `forceState(Idle)`；本规格以 2 次为最终拍板值 |
| 5 | 退出词检测 | LLM 回复含 "拜拜/退出/再见/睡觉" → 告别 → `forceState(Idle)` |
| 6 | 停顿阈值 | `kAsrResultIdleCommitMs` 800→400~500ms |
| 7 | LED 状态 | Listening 亮/Thinking 慢闪/Speaking 常亮/Idle 灭 |

## 四、SU-03T 验收标准

- [ ] **先做纯 SU-03T 单测**：仅初始化 `Serial + Su03tUart`，先不接 WiFi / Audio / Cloud，确认基础串口接收稳定
- [ ] 连续多次唤醒都能稳定收到 `[WAKE] SU-03T wake id=0x0`
- [ ] 播放 TTS 时不误触发（喇叭声音不被 SU-03T 当成唤醒词）
- [ ] 冷却时间 2.5s 内不重复进 Listening
- [ ] 只把“已知唤醒帧”当作 pass；**ASCII 行文本仅作调试日志，不作为正式唤醒成功判据**
- [ ] 如果出现上电/下载异常，优先怀疑 `GPIO0` 相关连线；V1 不以“ESP32 主动向 SU-03T 发命令”作为前提

### SU-03T 板测日志要求
- 串口至少打印：`[WAKE]`、`wake_id`、`cooldown hit`、`conversation start/end`
- 若收到无法识别的串口内容，保留原始 `reason` 日志，必要时补十六进制帧打印
- 板测记录至少要有 3 组：`正常唤醒`、`连续唤醒`、`播放 TTS 时误触发测试`
